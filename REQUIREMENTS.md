# ❤️ Księżniczka Bot — Telegram-бот для изучения польского

> Персональный бот-репетитор по польскому языку для одного человека (моей девушки, Любимой Даши).
> Карточки, стрики, валюта (по умолчанию ☀️ «солнышки»), магазин подарков и много тёплых сообщений.

---

## 1. Видение (Vision)

- **Кому:** одному пользователю, моей любимой Даше (+ администратор = автор бота).
- **Цель:** сделать так, чтобы ей было приятно и интересно заходить **каждый день**, проходить карточки и получать награды.
- **Тон:** тёплый, поддерживающий, с юмором. **Эмоциональное давление = 0** — бот никогда не «душнит» и не ругает за пропуски.
- **Фишка:** бот периодически напоминает, что он сделан именно автором (личные сообщения-сюрпризы).

**Актуальность зависимостей:** все версии языка, runtime, библиотек, ORM и инструментов должны быть актуальными стабильными версиями, доступными на момент имплементации в `2026` году. Для Node.js используется актуальная LTS-версия на момент разработки и деплоя. Версии фиксируются в `package.json` и lock-файле (`package-lock.json`/`pnpm-lock.yaml`); плавающие диапазоны и deprecated-пакеты не используются. Перед релизом зависимости проверяются на совместимость, уязвимости и наличие поддержки Node.js LTS 2026.

### 2.1. Репозиторий и деплой

- Исходный код хранится в публичном репозитории GitHub. Репозиторий не должен содержать секреты, реальные токены, production-переменные окружения или персональные данные.
- Деплой должен быть максимально простым: один Railway application service с одним persistent volume, смонтированным в `/data`, без отдельного database service, Dockerfile, Kubernetes, reverse proxy и worker service. Railway использует стандартный Node.js builder и автоматически деплоит основную ветку GitHub.
- Application service работает строго в одной реплике. Это предотвращает одновременный запуск нескольких экземпляров long polling и cron-задач; горизонтальное масштабирование в первой версии не поддерживается.
- Railway volume нельзя одновременно подключить к двум активным deployments, поэтому при redeploy допустима короткая пауза в работе бота; zero-downtime deploy для первой версии не требуется.
- Сборка: `npm ci && npm run build`. Railway pre-deploy command не используется для миграций, потому что volume в его контейнер не монтируется. Команда `npm run start` сначала выполняет `prisma migrate deploy` для `/data/kartochki.db`, затем запускает приложение; при ошибке миграции процесс завершается с ненулевым кодом.
- В production задаётся `DATABASE_URL=file:/data/kartochki.db`; локально используется `DATABASE_URL=file:./dev.db`. Файл production-БД запрещено размещать вне `/data`, поскольку файловая система deployment эфемерна.
- **Seed выполняется при старте бота, а не отдельной deploy-командой.** Сразу после проверки подключения к БД приложение делает идемпотентный посев: создаёт синглтоны `CurrencyConfig` и `EconomyConfig` со значениями по умолчанию, если их нет; добавляет стартовые категории/слова и `ContentText` из `src/db/seed.ts` и `src/content/seed.ts`, если соответствующих записей ещё нет. Существующие данные никогда не перезаписываются, повторный запуск безопасен. Для локальной разработки та же логика доступна командой `npm run seed`.
- Telegram работает только через long polling. Webhook в первой версии не реализуется.
- Отдельный HTTP-сервер, публичный домен и healthcheck endpoint не нужны. При старте приложение проверяет подключение к БД и завершается с ненулевым кодом при ошибке; Railway перезапускает упавший процесс.
- При `SIGTERM`/`SIGINT` приложение останавливает long polling и cron, закрывает Prisma, затем завершает процесс. В `README.md` описываются создание Railway project, подключение volume к `/data`, переменные окружения и команды deploy.
- Резервные копии SQLite не создаются: потеря данных допустима. Persistent volume нужен только для сохранения данных между обычными redeploy; удаление или повреждение volume может привести к полной потере данных.

### 2.2. Экономия ресурсов хостинга, Telegram API и БД

Бот рассчитан на одного основного пользователя, поэтому основная стоимость — постоянно работающий application service. SQLite хранится рядом с приложением и не требует отдельного оплачиваемого database service. Оптимизация не должна ослаблять транзакционность, идемпотентность или восстановление активной сессии.

**Application service и Telegram API:**

- Используется один процесс, один экземпляр `Bot` и одно long-polling соединение с длинным таймаутом Telegram `getUpdates`; busy polling и собственный частый цикл запросов запрещены. При сетевой ошибке применяется ограниченный exponential backoff с jitter, без плотного бесконечного retry-цикла.
- В `allowed_updates` запрашиваются только реально обрабатываемые типы update. Callback подтверждается один раз; одинаковый текст, клавиатура или уже показанный экран повторно не отправляются и не редактируются.
- Карточки продолжают использовать одно сообщение и `editMessageText` (§4.2). Новое сообщение отправляется только когда это часть UX; служебные промежуточные сообщения не создаются.
- Telegram Bot API сам по себе не тарифицируется за запрос, но лишние вызовы расходуют CPU, сеть и лог-квоту хостинга и повышают риск `429`. Ограничения `retry_after` соблюдаются; массовых параллельных отправок в первой версии нет.
- В production уровень pino по умолчанию `info`; SQL query logging Prisma и логирование каждого cron-тика отключены. Ожидаемые повторы update/callback не пишутся как error. Это уменьшает оплачиваемый объём логов.

**Планировщик:**

- Ежеминутный cron-тик выполняет только сравнение времени в памяти и при отсутствии задач делает **0 запросов к БД и 0 вызовов Telegram API**. Реестр `{ userId, timezone, reminderHour }` загружается при старте и обновляется в памяти сразу после создания пользователя или изменения настройки; после рестарта восстанавливается из БД.
- БД вызывается только для наступивших задач: утреннего/вечернего напоминания, сверки стрика в `00:05` и ежедневной очистки `ProcessedTelegramUpdate`. Перед отправкой напоминания одна короткая транзакция атомарно резервирует `ReminderDelivery`; Telegram вызывается только после коммита.
- Все задачи одного тика сначала группируются; запрещён шаблон «получить список пользователей, затем отдельным запросом проверить каждого» на каждом тике. При будущем росте аудитории обработка идёт ограниченными пакетами, без неограниченного `Promise.all`.
- Очистка `ProcessedTelegramUpdate` запускается один раз в сутки и удаляет старые строки пакетами, чтобы не создавать длинную блокировку и всплеск WAL.

**SQLite и Prisma:**

- На процесс создаётся ровно один `PrismaClient`. SQLite работает в режиме WAL с `busy_timeout = 5000`; при старте явно проверяются `PRAGMA journal_mode=WAL` и `PRAGMA foreign_keys=ON`. Транзакции короткие и не содержат сетевых вызовов, ожиданий пользователя или тяжёлых вычислений.
- Одновременно допускается только один писатель. Конфликты `SQLITE_BUSY` повторяются ограниченное число раз с коротким exponential backoff и jitter; бесконечные retry запрещены. Баланс, ответы и переходы статуса меняются атомарными условными `UPDATE`/`UPSERT` и уникальными ограничениями, а не PostgreSQL row-level locks.
- Каждый экран выбирает только нужные поля (`select`), а не полные relation-графы. Списки и админские логи имеют пагинацию; N+1-запросы запрещены, связанные записи читаются одним запросом или ограниченным числом пакетных запросов.
- `ContentText`, `CurrencyConfig` и `EconomyConfig` читаются через общий in-memory TTL-кэш. Повторные обращения в рамках одного update используют уже загруженное значение; после записи через админку соответствующий ключ инвалидируется немедленно.
- Статистика вычисляется только при открытии экрана SQL-агрегациями по доменным таблицам, а не загрузкой полного event log в Node.js; число запросов экрана ограничено константой. Детальные логи всегда читаются страницами.
- План обычной сессии и все вопросы теста строятся одним чтением необходимых кандидатов и сохраняются пакетно в существующей транзакции. Запрещены отдельный запрос на каждое слово, вариант ответа или карточку.
- Индексы из §9 обязательны; новые индексы добавляются только под подтверждённые частые фильтры. Каждый индекс ускоряет чтение, но увеличивает размер БД и стоимость каждой записи, поэтому дублирующие и неиспользуемые индексы не создаются.

**Функциональности, способные увеличить расход ресурсов:**

| Функциональность | Что расходует | Риск для текущего сценария | Требуемое ограничение |
| --- | --- | --- | --- |
| Постоянно запущенный Node.js | Оплачиваемые RAM/CPU даже без активности | Высокий, это основная фиксированная стоимость | Одна реплика, без отдельного database/worker/HTTP service |
| SQLite volume | Оплачиваемое дисковое место | Низкий при текущем объёме | Хранить только файл БД и следить за размером WAL |
| Минутный scheduler | CPU и запросы БД | Высокий при наивном опросе БД, низкий при реестре в памяти | Холостой тик не обращается к БД; запросы только при наступлении задачи |
| Event log и детальные админ-логи | Записи, индексы, место и чтение истории | В первой версии отсутствует | `NoopEventSink`; таблица `Event` остаётся пустой до явного включения |
| Статистика за всё время и тепловая карта | Aggregate queries по `Session`, `SessionCard`, `UserWord`, `UserDay` | Низкий: экран открывается редко и вручную | Константное число запросов при открытии экрана, без фонового пересчёта и без чтения `Event` |
| Генерация теста из 10 вопросов | Чтение пула слов и пакетная запись карточек | Низкий/средний при большом словаре | Одно чтение кандидатов, вычисления в памяти, одна пакетная запись |
| Runtime-тексты и конфиги | Частые мелкие чтения БД | Средний без кэша | TTL-кэш ≤ 30 секунд и повторное использование внутри update |
| Карточки и callback-кнопки | Telegram API, транзакции ответа, события | Пропорционален числу ответов и является полезной нагрузкой | Одно редактирование сообщения и одна транзакция на принятый ответ; дубли игнорировать |
| Напоминания и уведомления админу | Telegram API и проверка идемпотентности | Низкий для одного пользователя, линейный при росте аудитории | Не более одной отправки каждого типа на локальную дату, пакетная обработка |
| Подробные application/SQL-логи | CPU, I/O и оплачиваемое хранение логов | Средний при `debug`/query logging | В production `info`, без содержимого сообщений, payload и успешных cron-тиков |
| Seed при каждом старте | Чтения/записи БД и время запуска | Низкий при редких рестартах | Один транзакционный проход, bulk upsert/`createMany`, существующие строки не обновлять |

Оптимизация проверяется по метрикам Railway и размеру/времени запросов SQLite после появления реальной нагрузки. Не добавляются Redis, отдельный worker, PostgreSQL, материализованные представления или предварительные агрегаты, пока измерения не покажут, что SQLite и in-memory кэша недостаточно: для одного пользователя такая инфраструктура будет стоить дороже сэкономленных запросов.

### Переменные окружения

Все секреты и идентификаторы доступа (токен бота, строка подключения к БД, Telegram ID) хранятся **только** в локальном `.env`, который не коммитится в Git, и нигде не хардкодятся в исходном коде. В репозитории хранится только `.env.example` с примерами (без реальных значений):

```env
TELEGRAM_BOT_TOKEN=...
DATABASE_URL=file:./dev.db
ADMIN_TELEGRAM_ID=123456789
# через запятую, без пробелов; пусто = доступ открыт всем (см. §3.3) — не оставлять пустым в проде
ALLOWED_TELEGRAM_IDS=111111111,222222222
EVENT_LOG_ENABLED=false
TZ=Europe/Minsk
```

`ADMIN_TELEGRAM_ID` — обязательный целочисленный Telegram ID автора бота. Он валидируется через Zod при старте приложения. При отсутствии или неверном значении бот не запускается. Администратор всегда проходит проверку админских операций независимо от содержимого `ALLOWED_TELEGRAM_IDS`; остальные пользователи проверяются whitelist middleware.

`ALLOWED_TELEGRAM_IDS` — список целых Telegram ID через запятую, валидируется через Zod. В development/test пустое значение оставляет доступ открытым всем (см. §3.3). В production пустое значение считается ошибкой конфигурации: бот завершается до запуска long polling, чтобы случайно не открыть доступ любому пользователю Telegram, знающему его username.

`TZ` задаёт таймзону процесса Node.js по умолчанию (влияет на форматирование дат в логах и системные вызовы без явной таймзоны); бизнес-логика (стрики, лимиты, напоминания) не полагается на эту переменную. Вместо глобальной таймзоны бизнес-логика всегда явно конвертирует время в таймзону конкретного пользователя (`User.timezone`, см. §3.5 и §9), которая по умолчанию равна `Europe/Minsk`.

`.env` и реальные токены никогда не попадают в seed, логи, события или сообщения Telegram.

**Архитектура:** модульный монолит. Бизнес-логика (`core/`) полностью отделена от Telegram-слоя (`bot/`). Telegram — это только «тонкий» транспорт: принял апдейт → вызвал сервис → отрендерил ответ.

```
src/
  bot/            # grammY: команды, меню, кнопки, рендер экранов
  core/           # бизнес-логика (сервисы), не знает про Telegram
    learning/     # алгоритм карточек
    test/         # алгоритм теста (взвешенная случайность)
    economy/      # валюта (currency), магазин
    streak/       # стрики, щиты, досрочный стрик
    stats/        # агрегация статистики по доменным таблицам (§4.6, §11.1)
    events/       # типы событий и EventSink; в первой версии используется NoopEventSink
  content/        # seed/fallback для текстов; рабочие тексты хранятся в БД
    seed.ts        # первоначальные тексты для заполнения БД
    service.ts     # получение текста из БД, кэш и fallback
  scheduler/      # cron-задачи (напоминания)
  db/             # Prisma client, seed
  config/         # env, whitelist
prisma/
  schema.prisma
prisma.config.ts   # provider sqlite и DATABASE_URL для Prisma CLI
```

**Принцип:** рабочие тексты и варианты сообщений хранятся в SQLite и загружаются через `content/service`. Администратор может добавлять, изменять, отключать и переименовывать тексты во время работы бота; rebuild и перезапуск не требуются. `src/content/seed.ts` используется только для первоначального заполнения БД и как fallback при отсутствии записи.

Ключ текста стабилен и не зависит от формулировки сообщения (например, `reminder.morning`, `praise.session_finished`, `surprise.random`). У одного ключа может быть несколько активных вариантов, из которых бот выбирает случайный, исключая (если активен более чем один вариант) тот, что был показан этому пользователю последним для данного ключа. Последний показанный вариант хранится в `UserContentState` (см. §9) и обновляется `upsert`-ом в тот же момент, когда вариант выбран для отправки. Номер `variant` присваивается автоматически (максимальный существующий `variant` для ключа + 1) при добавлении через админку — админ его не вводит вручную. Сервис использует короткий TTL-кэш (не более 30 секунд) и сразу очищает его после изменения текста через админку. При изменениях напрямую в БД новые значения становятся видны после истечения TTL.

Seed может содержать несколько вариантов одного ключа: они получают стабильные номера `0..N` и `isSeed = true`. Обычный повторный seed отсутствующие seed-варианты добавляет, но существующие строки не изменяет. Действие «Восстановить seed» явно заменяет текст выбранного seed-варианта значением из `src/content/seed.ts`, включает его и инвалидирует кэш; пользовательские варианты с `isSeed = false` не затрагиваются.

## 3. Ключевые доменные правила

### 3.1. Валюта (по умолчанию ☀️ «солнышки», конфигурируется в рантайме)

- Название и иконка валюты **не хардкодятся**: хранятся в `CurrencyConfig` (см. §9, синглтон-запись), редактируются админом во время работы бота без rebuild и перезапуска, кэшируются так же, как тексты (TTL ≤ 30 секунд, см. §2). Значения по умолчанию (seed): иконка `☀️`, формы названия «солнышко / солнышка / солнышек» (`nameOne` / `nameFew` / `nameMany`). Выбор формы для конкретного числа выполняется по стандартному правилу склонения числительных в русском языке (по остатку от деления на 10 и на 100), а не по грубому диапазону вида «5–20» — иначе числа `21`, `101` и т.п. будут показаны с неверным окончанием. Во внутреннем коде, моделях и событиях используется нейтральное имя `currency`, а не «sun»/«солнышко», чтобы переименование валюты не требовало правок бизнес-логики.
- Обычная сессия содержит до `10` уникальных активных карточек. Если в категории доступно меньше `10` слов, в план сессии включаются все доступные слова без повторов. Валюта начисляется после ответа на все карточки созданного плана (`plannedCount`, от `1` до `10`) — `5` единиц независимо от количества правильных ответов. Пустую сессию запустить нельзя.
- Тест состоит из `10` вопросов. Валюта начисляется только за полностью пройденный тест — `10` единиц. Награда за отдельные вопросы не начисляется.
- Если сессия завершена досрочно кнопкой `Закончить`, уже принятые ответы и прогресс слов сохраняются, но валюта и стрик не начисляются.
- Общий лимит наград за обучение — `20` единиц валюты в календарные сутки.
- Если очередная полностью пройденная сессия превысит дневной лимит, сессия и стрик всё равно засчитываются, но валюта за неё не начисляется. Бот отправляет мягкое сообщение с текущим названием валюты, например: «Ты сегодня уже заработала максимум ☀️ солнышек. Давай теперь немного отдохнём, ты умница ❤️».
- Редкий сюрприз даёт `1–3` единицы валюты, не более одного сюрприза в сутки.
- Валюта тратится в магазине. Баланс не может стать отрицательным.
- Админ может **начислить валюту** пользователю вручную: указывает сумму (целое положительное число) и непустую причину длиной до `500` символов. `requestId` равен `callback_query.id` кнопки окончательного подтверждения. Операция атомарно увеличивает `User.currencyBalance`, создаёт `CurrencyTransaction` с `reason = ADMIN` и ключом `ADMIN_GRANT:{userId}:{requestId}`, а также `AdminAdjustment` с тем же ключом и введённой причиной. Отдельное событие не формируется. Начисление не считается обучением: не влияет на дневной лимит наград (§3.1, §8) и не обновляет стрик.

### 3.2. Стрик 🔥

- Стрик обновляется только за полностью пройденную сессию: все карточки зафиксированного плана обычной сессии (`1–10`) или все `10` вопросов теста.
- Досрочное завершение кнопкой `Закончить`, выход или ошибка не обновляют стрик, хотя статистика по отвеченным карточкам записывается.
- Сутки — календарный интервал от `00:00:00` до `23:59:59.999` по таймзоне пользователя (`User.timezone`, по умолчанию `Europe/Minsk`, см. §3.5).
- Состояние каждого локального дня хранится в `UserDay` с датой `YYYY-MM-DD`. День поддерживает стрик, если его статус `COMPLETED`, `EARLY` или `SHIELDED`. Первая полная сессия дня создаёт или обновляет запись в `COMPLETED`; последующие полные сессии только увеличивают `completedSessions` и не увеличивают стрик повторно.
- Перед любой операцией со стриком сервис последовательно сверяет необработанные даты до текущей локальной даты включительно. Для каждой даты порядок правил фиксирован: `COMPLETED` увеличивает серию на `1`; заранее созданный `EARLY` увеличивает её на `1` при наступлении этой даты; `SHIELDED` сохраняет текущее значение без увеличения; `MISSED` обрывает серию. Если прошедший день не имеет статуса, при наличии щита создаётся `SHIELDED` и списывается ровно один щит, иначе создаётся `MISSED`. Текущий день без активности не помечается пропущенным.
- Сверка запускается cron-задачей ежедневно в `00:05` по локальному времени каждого пользователя (планировщик тикает раз в минуту и сравнивает текущее время в `User.timezone` с `00:05`) и дополнительно перед завершением сессии, покупкой/применением щита, показом стрика и отправкой напоминания. Поле `UserDay.streakAppliedAt`, уникальные ограничения и атомарные условные изменения внутри короткой SQLite-транзакции делают каждый переход идемпотентным. Если серия была оборвана одним или несколькими `MISSED`, первая последующая полная сессия создаёт новую серию со значения `1`.
- **Щит** — покупается в магазине и применяется **автоматически**: при пропущенном дне один щит списывается и защищает стрик за этот день. Щиты суммируются и расходуются по одному за каждый пропущенный день, пока не закончатся; максимальное количество щитов на руках не ограничено — можно накопить сколько угодно.
- **Досрочный стрик** — после 3 полных сессий за день можно создать запись `EARLY` строго на следующую локальную дату. Активация сегодня только создаёт бронь и не меняет число стрика; прибавление происходит при наступлении забронированной даты. Одновременно разрешена только одна будущая запись `EARLY`. Если пользователь учится в этот день, статус атомарно меняется на `COMPLETED`, бронь считается использованной и повторно стрик не увеличивается. Если не учится, `EARLY` сохраняет стрик без расхода щита. Новую бронь можно получить только после 3 полных сессий уже в новом дне. Предложение активировать (кнопка `Активировать`) не показывается повторно после завершения очередной сессии в тот же день, если бронь на завтра уже сделана.
- Вечернее напоминание отправляется ровно в `21:00` по локальному времени пользователя (`User.timezone`), если сегодняшний `UserDay` не имеет статуса `COMPLETED` или `EARLY`; защищённый прошлый день не подавляет напоминание на сегодня. Повторная отправка в тот же день запрещена записью `ReminderDelivery` с ключом `EVENING:{userId}:{localDate}` (§5.1).
- Админ может **вернуть стрик** вручную: указывает восстанавливаемое неотрицательное значение и непустую причину длиной до `500` символов. `requestId` равен `callback_query.id` кнопки окончательного подтверждения. Операция меняет `currentStreak`, не уменьшает `maxStreak`, создаёт идемпотентную запись `AdminAdjustment` с ключом `STREAK_RESTORE:{userId}:{requestId}`, не создаёт событие и не переписывает календарные статусы прошлых дней.

#### Эмоции и приколюхи стрика

- После успешного завершения первой сессии за день бот показывает текущий стрик: `🔥 7 дней подряд` и короткую случайную фразу из runtime-контента.
- Для вех `1`, `3`, `7`, `14`, `30`, `50` и `100` дней отправляется особое поздравление. Текст каждой вехи имеет несколько вариантов.
- При новом личном рекорде бот сообщает об этом отдельно: `🏆 Новый рекорд — N дней!`.
- На значениях стрика из декларативного списка титулов (см. §3.2.1) бот показывает тематический титул, например `Умница-красавица` (7 дней) или `Pani Kochana` (30 дней).
- **Всё одним сообщением.** Текущий стрик, веха, новый личный рекорд и титул собираются в одно сообщение в фиксированном порядке блоков: стрик → веха → рекорд → титул. Несколько отдельных сообщений подряд не отправляются. Отсутствующие блоки просто опускаются. Сообщения о сработавшем щите и о сюрпризе — отдельные.
- После 3 полностью пройденных сессий за день бот предлагает досрочно закрыть следующий день; при активации отправляет отдельную благодарность и обновляет статус досрочного стрика.
- Щит применяется автоматически: при пропущенном дне бот списывает один щит и сообщает, что день защищён: `🛡️ Щит сработал — твой огонь сохранён`. За один пропущенный день расходуется не более одного щита.
- Если стрик потерян, бот не ругает и не использует формулировки про провал. Он сообщает новый стрик и поддерживает возвращение: `Ничего страшного. Начнём новую серию? 🔥`.
- Эмоциональное сообщение за стрик не даёт валюту автоматически. Случайный подарок-сюрприз может сработать отдельно по правилам экономики.
- Повторная обработка одной сессии не повторяет поздравление, веху или уведомление о новом рекорде.

#### 3.2.1. Титулы стрика

Титул подбирается декларативным списком «стрик → титул» (`src/content/streakTitles.ts`), отсортированным по возрастанию `streak`; при достижении `currentStreak`, точно равного одному из значений списка, бот показывает соответствующий титул вместе с обычным сообщением о стрике. Добавление нового звания — это одна новая строка `{ streak, title }` в списке, без изменения бизнес-логики подбора. Титулы для `3`, `7` и `14` дней — на русском; начиная с `30` дней титулы даются на польском (тематически, как маленькая награда за долгую серию изучения языка).

| Стрик (дней) | Титул                |
| ------------ | -------------------- |
| `3`          | Солнышко моё ☀️      |
| `7`          | Умница-красавица     |
| `14`         | Моя гордость         |
| `30`         | Pani Kochana         |
| `50`         | Najlepsza na świecie |

Список можно расширять любыми промежуточными или более высокими значениями; повторный показ одного и того же титула для уже пройденного значения не выполняется (см. правило об идемпотентности обработки сессии выше).

### 3.3. Белый список и видимость контента

- Список Telegram ID в конфиге.
- Список **пуст** → доступ открыт всем только в development/test; в production бот не запускается.
- Список **не пуст** → доступ только у указанных ID.
- Обычный пользователь видит активные системные категории (`Category.ownerId = null`) и собственные активные категории (`ownerId = userId`). В видимой категории ему доступны активные системные слова (`Word.ownerId = null`) и собственные активные слова; слова и категории других пользователей не читаются, не изменяются и не попадают в планы, тесты или саммари.
- Слово, добавленное пользователем в системную категорию, получает `Word.ownerId = userId`. В пользовательской категории и категория, и все её слова принадлежат одному пользователю. Администратор может просматривать и деактивировать контент любого владельца.

### 3.4. Деактивация слов и категорий

- **Физического удаления контента нет.** Слова и категории не удаляются из БД ни пользователем, ни администратором.
- Пользователь может деактивировать только собственные слова и категории (`isActive = false`). Администратор может деактивировать контент любого владельца. Деактивация категории в той же транзакции деактивирует все её слова.
- История, `UserWord`, `SessionCard`, `WordOfDay` и уже созданные планы сохраняются. Активная сессия продолжает использовать зафиксированные снимки контента и не переводится в `ABANDONED`. Деактивированный контент не попадает только в новые планы, тесты, саммари и новые назначения слова дня.
- Повторная активация доступна администратору; категория и её слова активируются отдельными явными действиями, без неявной каскадной реактивации слов.

### 3.5. Таймзона

- Таймзона привязана к пользователю (`User.timezone`, см. §9), а не к процессу или конфигу целиком. Значение по умолчанию для всех пользователей — `Europe/Minsk`; выбор другой таймзоны пользователем в UI не реализуется в первой версии, но модель данных уже это допускает.
- Все напоминания, календарные дни, стрики, дневные лимиты и статистика считаются по времени `User.timezone` конкретного пользователя. Там, где в этом документе указано `Europe/Minsk`, имеется в виду значение таймзоны пользователя по умолчанию; при появлении настройки выбора таймзоны (см. §4.7) все эти правила продолжают действовать, но используют сохранённое значение `User.timezone` вместо константы.
- Бизнес-логика всегда явно конвертирует время в таймзону пользователя средствами библиотеки работы с датами и не полагается на системную таймзону процесса. Переменная окружения `TZ` (см. §2) влияет только на дефолтное форматирование дат/логов Node.js, но не является источником истины для бизнес-правил.

## 4. Функциональность

### 4.1. Главное меню

`Учиться` · `Добавить слово` · `Настройки` · `Магазин` · `Админ` (только для админа)

Главное меню показывает баланс валюты, текущую серию и количество щитов на руках (`🛡️ Щиты: N`, включая `0`), чтобы не открывать отдельный экран ради этого. Если на текущую локальную дату назначено слово дня (§6.5), под этими строками добавляется блок `❤️ Слово дня: kocham — любить`; при отсутствии записи блок не показывается.

В разделе `Админ` должен быть экран `Тексты`: список ключей с поиском и фильтром по группе, просмотр всех вариантов, добавление/редактирование/отключение варианта и восстановление seed-значения. После сохранения новый текст используется ботом без rebuild и перезапуска.

Также в разделе `Админ` должен быть экран `Валюта`: редактирование иконки и трёх грамматических форм названия (`nameOne` / `nameFew` / `nameMany`) в `CurrencyConfig`. Изменения применяются сразу во всех экранах (баланс, цены, награды), без rebuild и перезапуска.

И экран `Экономика`: редактирование полей `EconomyConfig` (награды за сессию и тест, дневной лимит, цены товаров). Правила те же, что у `CurrencyConfig`: все значения — целые числа `>= 0` (валидация Zod), TTL-кэш ≤ 30 секунд с немедленной инвалидацией после сохранения, без rebuild и перезапуска. Изменение конфига действует только на будущие операции и не переписывает историю (§8).

### 4.2. Обучение (Учиться)

1. Показывается **Тест** + список категорий.
2. Выбор категории → показывается **саммари категории**, затем выбор режима: **🇵🇱 польский** или **🇷🇺 русский**.
3. Карточки идут по очереди.

**Карточка:** слово (на польском или русском) + 3 кнопки: `Знаю` · `Не знаю` · `Закончить`.

**Визуальный вид карточки:** оформление простое и не перегруженное — крупное слово по центру и прогресс-бар текущей сессии из эмодзи-квадратиков (🟩 — пройдено, ⬜ — осталось) с числом `N/plannedCount`, например:
```
🇵🇱 kot

🟩🟩🟩⬜⬜⬜⬜⬜⬜⬜  3/10
```
Прогресс-бар обновляется в том же сообщении (`editMessageText`) при переходе к следующей карточке, без отправки новых сообщений на каждый шаг. Дополнительных иконок, рамок и картинок карточка не содержит — вся «изюминка» экрана именно в прогресс-баре и коротких тёплых репликах бота вокруг него (см. §6.3).

#### 4.2.1. Саммари категории

Сразу после выбора категории (до выбора режима PL/RU) бот показывает короткую сводку по активным словам категории:

- **Всего слов** — число активных слов категории.
- **Пройдено** — число активных слов с `UserWord.timesKnown > 0`, то есть тех, на которые хотя бы раз был ответ «Знаю» (совпадает с понятием «Доступно для Теста» из §4.2). Последующее «Не знаю» этот счётчик не сбрасывает.
- **Выучено** — число активных слов с `UserWord.currentLevel = 2` (см. §11.1).
- **Осталось выучить** — `Всего слов − Выучено`.
- **Нужно повторить** — число активных слов с `UserWord.lastAnswer = 'UNKNOWN'`, то есть слов, чей самый последний ответ был «Не знаю» и ещё не был перекрыт повторным «Знаю».

Слово без единого ответа (`timesSeen = 0`) считается только в «Всего слов» и «Осталось выучить», в «Нужно повторить» не входит. Саммари считается на момент открытия экрана и не хранится отдельной записью; повторное открытие пересчитывает его заново.

У пользователя может быть только одна сессия со статусом `ACTIVE`, независимо от режима. При входе в обучение бот предлагает продолжить её или завершить кнопкой `Закончить`; создать другую сессию до закрытия активной нельзя. Ограничение обеспечивается транзакцией и частичным уникальным индексом SQLite по `userId WHERE status = 'ACTIVE'`.

Обычная сессия состоит максимум из `10` карточек. При старте список фиксируется в `SessionCard`: выбираются `min(10, число доступных активных слов)` уникальных слов категории. Если доступных слов меньше `10`, сессия сокращается и показывает каждое доступное слово один раз; если нет ни одного — запуск запрещён с мягким сообщением. Последующая деактивация слова или категории не меняет уже созданный план: сохранённая карточка остаётся доступной до закрытия сессии. Карточка считается пройденной после ответа `Знаю` или `Не знаю`; ответ и прогресс `UserWord` сохраняются сразу.

**Терминология (два разных понятия, не подменять в коде):**

- **Доступно для Теста** — `timesKnown > 0`, то есть на слово хотя бы раз за всю историю был ответ `Знаю`. Только такие слова могут быть целевыми словами вопроса Теста (§4.3).
- **Выучено** — `currentLevel = 2`. Именно это значение используется в саммари категории (§4.2.1) и в статистике (§11.1).

- После ответа на последнюю карточку зафиксированного плана сессия автоматически завершается полностью: фиксируется `SESSION_FINISHED`, обновляется стрик и начисляется награда за сессию (с учётом дневного лимита). Дополнительное нажатие `Закончить` не требуется.
- Если пользователь нажал `Закончить` раньше, сессия завершается досрочно: формируется `SESSION_ABANDONED`, уже принятые ответы сохраняются, но стрик и награда **не** начисляются.
- Сессия закрывается один раз. Повторный callback ответа или `Закончить` не создаёт новую сессию, не меняет стрик и не начисляет награду.

Активная сессия не протухает автоматически и восстанавливается из `Session`/`SessionCard` после перезапуска. Явный `Закончить` переводит её в `ABANDONED`. Системная ошибка оставляет сессию `ACTIVE`, если транзакция ответа не была завершена; пользователь может продолжить её после восстановления.

**Алгоритм подбора карточек в категории** (взвешенная выборка без повторов).

`currentLevel` пересчитывается по первому подошедшему правилу, строго в этом порядке:

```
currentLevel = 0 (новое),       если timesSeen = 0
currentLevel = 2 (знакомое),    иначе если consecutiveKnown >= 3 И currentScore >= 2
currentLevel = 1 (незнакомое),  во всех остальных случаях
```

После `Знаю`: `timesSeen += 1`, `timesKnown += 1`, `consecutiveKnown += 1`, `consecutiveUnknown = 0`, `currentScore = min(5, currentScore + 1)`. После `Не знаю`: `timesSeen += 1`, `timesUnknown += 1`, `consecutiveUnknown += 1`, `consecutiveKnown = 0`, `currentScore = max(-5, currentScore - 1.5)`. Затем пересчитывается `currentLevel` по правилам выше. В обоих случаях `lastAnswer`/`lastAnswerAt` обновляются на актуальный ответ.

**Повторный «Знаю» после «Не знаю»:** если перед текущим ответом `UserWord.lastAnswer = 'UNKNOWN'`, а новый ответ — `Знаю`, слово считается повторённым: помимо обычных полей выше, сервис выставляет `nextReviewAt = now + 24 часа` (по `Clock`, см. §11). Пока `nextReviewAt` не наступил, слово имеет низший приоритет при подборе карточек и берётся в план только по правилам fallback ниже. После наступления `nextReviewAt` слово возвращается в обычную выборку по текущему `currentLevel`. Деактивация слова/категории или явное решение пользователя переучить слово не влияют на уже созданный план текущей сессии (см. правило выше).

**Fallback, если все слова на кулдауне:** фильтр по `nextReviewAt` — мягкий. Сначала план набирается только из слов без активного `nextReviewAt`. Если таких слов не хватает до `10` (в том числе когда их `0`), оставшиеся слоты заполняются словами на кулдауне — в порядке возрастания `nextReviewAt` (сначала те, чей кулдаун ближе всего к истечению), без повторов внутри плана. Сессия запрещена только тогда, когда в категории вообще нет активных слов. Саммари категории (§4.2.1) считается по всем активным словам и кулдаун не учитывает.

Вес слова при создании плана:

```
base = currentLevel == 0 ? 6 : currentLevel == 1 ? 3 : 1
weight = base + min(timesUnknown, 5) * 0.4 + min(consecutiveUnknown, 3) * 0.6
```

Из слов выполняется последовательная случайная выборка пропорционально `weight` с удалением уже выбранного слова. Поэтому новые и трудные слова встречаются чаще, но знакомые не исчезают полностью. Для воспроизводимых тестов генератор случайных чисел передаётся как зависимость.

**Раскрытие правильного ответа при «Не знаю»:** `SessionCard.translationText` хранит снимок перевода показываемого слова (противоположный язык относительно `promptText`), зафиксированный в момент создания плана — так же, как `promptText`. Если ответ на карточку — `Не знаю`, бот показывает отдельным экраном пару «слово — перевод» и кнопку `▶️ Дальше`; только после её нажатия открывается следующая карточка. Ответ `Знаю` этот экран не показывает и сразу ведёт к следующей карточке. Для вопросов Теста (§4.3) правильный вариант и так виден среди кнопок, поэтому отдельное раскрытие не требуется.

**Будущее расширение (заложить в модель, реализовать позже):**

- Транскрипция польского слова.
- Spaced repetition (поле `nextReviewAt` уже в модели).

### 4.3. Тест 🎯 (отдельный алгоритм)

**Прогресс-бар:** во время теста квадраты прогресс-бара красятся по правильности уже данных ответов — 🟩 за верный, 🟥 за неверный, ⬜ для ещё не отвеченных вопросов; в обычной сессии карточек прогресс остаётся однотонным 🟩/⬜ (без цвета ошибки).

Тест состоит из `10` вопросов. Целевые слова берутся только из **доступных для Теста** слов, то есть из слов с `timesKnown > 0` — на которые пользователь хотя бы раз за всю историю ответил `Знаю` (см. терминологию в §4.2; текущее значение `lastAnswer` при этом роли не играет). Целевые слова выбираются из разных доступных категорий, насколько это возможно; если категорий или слов недостаточно, допускаются повторы.

**Формат вопроса:** показывается польское слово, пользователь выбирает правильный русский перевод из `4` вариантов. Один вариант правильный, три других — русские переводы других активных слов **из той же категории, что и целевое слово**. Варианты перемешиваются.

Для каждого вопроса сохраняются целевое слово, категория, все 4 варианта, позиция правильного ответа и выбранный вариант. Это позволяет корректно проверить callback и восстановить тест после перезапуска.

**Момент генерации:** все `10` вопросов создаются сразу при старте теста, в одной транзакции вместе с `Session`, и записываются в `SessionCard` с `position = 0..9`. Правила состава `4/3/2/1`, cooldown и выбор категории «с минимальным числом уже созданных вопросов» применяются именно на этом этапе. `SessionCard.promptText` хранит снимок польского слова, а `options` — упорядоченный JSON-массив ровно из четырёх объектов `{ wordId: number, label: string }`, где `label` является снимком русского перевода. Структура валидируется Zod при записи и чтении. `SessionCard.shownAt` заполняется позже — в момент фактического показа вопроса пользователю (поле nullable), чтобы `responseTimeMs` считался корректно. Для обычной сессии `promptText` также хранит снимок показываемого слова в выбранном направлении. Поэтому редактирование или деактивация исходного слова не меняет активную сессию.

**Взвешенная случайность** (не «худшее слово всегда»):

```
weight = difficulty × freshness × uncertainty
```

- `attempts = testCorrectCount + testWrongCount`.
- `accuracy = (testCorrectCount + 1) / (attempts + 2)` — сглаженная точность, чтобы новые для теста слова не считались крайними.
- `difficulty = 0.5 + 2 × (1 - accuracy)` — диапазон `0.5..2.5`.
- `uncertainty = 1 + 2 × (4 × accuracy × (1 - accuracy))` — диапазон `1..3`, максимум у нестабильных слов около `50%`.
- `freshness = 1.3`, если слово ещё не было целью сегодня или с прошлого показа прошло не менее `10` вопросов; `1.0`, если прошло `8–9` вопросов (минимально допустимая дистанция после cooldown в `7` вопросов равна `8`); `0.5` при вынужденном нарушении cooldown.

Для состава `4/3/2/1` слова делятся по сглаженной точности: сложные `< 0.45`, средние `0.45..<0.75`, хорошо известные `>= 0.75`; слова без ответов в тесте относятся к средним. Последний слот выбирается из всего пула. Значения `4/3/2/1` являются целевыми квотами: если в нужной группе нет допустимого кандидата без cooldown, слот заполняется кандидатом без cooldown из общего пула независимо от группы. Категория с минимальным числом уже созданных вопросов выбирается только среди категорий, в которых есть кандидат для текущего шага; при равенстве категория выбирается через внедряемый RNG, затем слово выбирается по весу. Если кандидатов без cooldown нет вообще, применяется fallback следующего абзаца. Фактическая группа выбранного слова не меняет типы оставшихся слотов. Это обеспечивает разнообразие категорий без зависания на пустой группе.

**Cooldown:** целевое слово не появляется в следующих `7` вопросах пользователя. Счётчик сквозной за календарные сутки и учитывает все тесты. Исторический порядок определяется только фактически показанными тестовыми `SessionCard` текущей локальной даты: по `shownAt`, а при равенстве — по `sessionId` и `position`. При генерации нового теста к этой истории последовательно добавляется уже сгенерированный префикс текущего плана; ещё не показанные карточки старой активной сессии отсутствовать не могут из-за ограничения одной `ACTIVE`-сессии. Если после фильтра нет кандидата для текущего слота, сначала разрешается кандидат другой группы без cooldown, а затем — слово на cooldown с наибольшим числом вопросов после прошлого показа и `freshness = 0.5`; при равенстве используется взвешенный выбор. При наличии минимум двух допустимых целей одно слово не показывается два раза подряд; при наличии минимум пяти — не более двух раз за один тест.

**Обязательный состав теста из 10 вопросов:**
| Тип | Кол-во |
|-----|--------|
| Сложные | 4 |
| Средние | 3 |
| Хорошо известные | 2 |
| Случайное | 1 |

Правило: даже «5 раз не знаю» слово **не занимает весь тест**.

**Минимум слов:** для каждого вопроса из БД выбираются целевое слово и ещё `3` других активных слова строго той же категории: для цветов — четыре цвета, для еды — четыре слова о еде и т.д. В категории должно быть минимум `4` активных слова с `4` различными русскими переводами после нормализации (`trim`, приведение к нижнему регистру и схлопывание пробелов), иначе она не участвует в тесте. Целевое слово обязательно доступно для Теста (`timesKnown > 0`); отвлекающие слова могут быть недоступны для Теста и выбираются равновероятно без повторов среди подходящих слов категории, исключая цель и уже выбранные нормализованные переводы. Если нет ни одной подходящей категории с изученной целью, тест недоступен и бот мягко предлагает сначала пройти карточки. Если изученных целей меньше `10`, повторы разрешены по правилам cooldown. Четыре выбранных `wordId` и снимки их переводов сохраняются в `SessionCard.options`, поэтому последующее редактирование БД не меняет уже созданный вопрос.

После ответа на 10-й вопрос тест автоматически закрывается: формируется `SESSION_FINISHED`, начисляется награда `10` единиц валюты и обновляется стрик. При `NoopEventSink` событие не сохраняется в `Event`. Досрочно прерванный тест засчитывается как незавершённый: уже принятые ответы сохраняются, стрик и награда не начисляются.

**Саммари теста:** сразу после завершения теста отдельным сообщением показывается список всех `10` вопросов с результатом по каждому — польское слово, правильный перевод, отметка ✅/❌ и (только для неверных ответов) перевод, выбранный пользователем. Саммари строится по сохранённым `SessionCard` завершённой сессии и не показывается для обычных сессий с карточками.

### 4.4. Добавление слов

- Пользователь добавляет слово в существующую категорию **или** создаёт новую категорию. Ввод разбит на два последовательных шага: сначала бот запрашивает польское слово, затем — его русский перевод; слово сохраняется только после получения обоих значений.
- Может деактивировать свои слова/категории (`isActive = false`); деактивация категории каскадно деактивирует её слова (§3.4). Физического удаления нет.

### 4.5. Магазин 🛍️

Показывает текущий баланс валюты (иконка и название берутся из `CurrencyConfig`, по умолчанию ☀️ «солнышки») и кнопки:

- `🎁 Маленький подарок` (`120` ☀️) · `💝 Особый подарок` (`350` ☀️)
- `🛡️ Щит на стрик` (`25` ☀️) — покупается многократно, суммируется и применяется автоматически.

**Каждая покупка:**

- Проверяет баланс и списывает валюту атомарно; баланс не может уйти в минус.
- Результат хранится в `Purchase` и `CurrencyTransaction`; отдельные события покупки и списания не формируются.
- Присылает уведомление **админу** с информацией, что куплено.

### 4.6. Статистика 📊

Кнопка `📊 Статистика` есть в главном меню. Все показатели считаются агрегациями по доменным таблицам `Session`, `SessionCard`, `UserWord` и `UserDay` в момент открытия экрана; `Event` не используется, поэтому период работы с `NoopEventSink` не теряется. Число SQL-запросов константно и не растёт вместе с историей.

**📚 Всего:** выучено слов, изучено карточек, тестов, правильных ответов, % правильных.
**🔥 Серия:** текущий стрик, максимальный стрик, дней обучения, пропущено дней, использовано щитов.
**⏱️ Время:** всего времени обучения, средняя сессия, самая длинная сессия.
**🕐 Привычки:** любимое время (утро/день/вечер), любимый день недели, среднее число сессий в день.
**Среди дня/вечером** — временные букеты для «любимого времени» в статистике (по таймзоне пользователя, `User.timezone`, по умолчанию `Europe/Minsk`): **утро** `05:00–11:59`, **день** `12:00–17:59`, **вечер** `18:00–04:59` (включая ночь, чтобы покрыть все 24 часа без четвёртого бакета).

**🧠 Слова:** самое лёгкое и самое сложное (по наибольшему/наименьшему `UserWord.currentScore`), чаще всего забываемое, выученное быстрее всего, потребовавшее больше всего повторений.
**🔥 Тепловая карта активности** (GitHub-style): активность по дням текущего **календарного месяца** (с 1-го числа по сегодняшний день включительно, по таймзоне пользователя), текстовая шкала эмодзи. Источник — `UserDay.completedSessions` за соответствующие `localDate`.
**🎯 Трудные слова:** топ-5 «Не знаю» за всё время (только список, без запуска отдельной сессии).

Точные определения и правила разрешения равенств для этих метрик приведены в §11.1; экран статистики не вводит собственные формулы.

### 4.7. Настройки ⚙️

- **Час утреннего напоминания** — пользователь выбирает только целый час от `0` до `23` (минуты не настраиваются, напоминание всегда приходит в `:00`). Значение сохраняется в `User.reminderHour` (целое, валидация Zod `0..23`) и применяется со следующего cron-тика, без перезапуска. В UI выбор делается кнопками со значениями вида `07:00`, `08:00`, …
- Таймзона хранится per-user (`User.timezone`, по умолчанию `Europe/Minsk`); экран выбора таймзоны — расширение будущей версии (см. §10, Фаза 8), в первой версии значение не редактируется пользователем через UI.

### 4.8. Админка 🧑‍💻

- Просмотр пользователей: имя/username из Telegram (`User.firstName`/`User.username`, с запасным вариантом на `Telegram ID`, если они не заданы), Telegram ID, текущий стрик, макс. стрик, баланс валюты.
- **Деактивация и повторная активация слов/категорий.** Администратор может менять `isActive` у контента любого владельца. Деактивация категории каскадно деактивирует её слова в одной транзакции; реактивация категории не активирует слова автоматически. Операция не удаляет зависимости и не меняет баланс, прогресс или историю.
- Если деактивируемое слово или категория задействованы в `ACTIVE`-сессии, сессия не прерывается и продолжает использовать снимки из `SessionCard`. Контент исключается только из новых сессий, тестов и назначений слова дня.
- **Вернуть стрик** пользователю.
- **Отправить сообщение** пользователю от имени бота: админ вводит текст (до `3500` символов) и подтверждает отправку отдельной кнопкой. Запись `AdminMessage` с ключом `ADMIN_MESSAGE:{userId}:{requestId}` резервируется до вызова Telegram, поэтому повторное нажатие не отправляет сообщение второй раз (семантика at-most-once, как у напоминаний). Текст уходит без HTML-разметки; событие не формируется.
- **Начислить валюту** пользователю: указывается сумма и причина, применяются правила из §3.1 (не влияет на дневной лимит и стрик, идемпотентно по `requestId`).
- Редактировать **название и иконку валюты** (`CurrencyConfig`) — экран `Валюта`, и **параметры экономики** (`EconomyConfig`) — экран `Экономика`, см. §4.1.
- Детальные логи по дням/сессиям в первой версии отсутствуют. Будущий экран сможет показывать карточки, ответы, время ответа и предыдущие ответы только после явного включения истории.

Пока `EVENT_LOG_ENABLED=false`, никакие действия не записываются в `Event`; для диагностики достаточно структурированного лога pino. Даже после включения event log админские, экономические и служебные действия туда не попадают: сохраняются только типы из §5, необходимые пользовательской статистике.

```
19:05 — "kot" → НЕ ЗНАЮ (4.8 сек)
```

## 5. События пользовательской статистики (сохранение в БД отложено)

В первой версии доменные события **не записываются в БД**, экран истории отсутствует, а статистика (§4.6) считается по доменным таблицам, а не по `Event`. При этом весь прикладной код формирует типизированные события в местах изменения состояния, чтобы позднее включить event log без переписывания бизнес-сервисов.

- `core/events` содержит только события, необходимые будущей пользовательской статистике, и интерфейс `EventSink.record(transaction, events)`; только операции, перечисленные ниже, вызывают этот интерфейс.
- В production первой версии подключён `NoopEventSink`: он не выполняет SQL-запросы и не создаёт строки `Event`. Значение `EVENT_LOG_ENABLED=false` является обязательным значением по умолчанию.
- `PrismaEventSink` и его тесты реализуются сразу, но адаптер не подключается, пока `EVENT_LOG_ENABLED=false`. При будущем включении он записывает события пакетно в той же транзакции, что и доменное изменение.
- Таблица `Event` и типизированный реестр событий остаются в Prisma-схеме как подготовленная инфраструктура; до включения флага таблица остаётся пустой.
- Идемпотентность бизнес-операций не зависит от `Event`: ответы защищает `SessionCard.answerActionId`, деньги — ключи `CurrencyTransaction`/`Purchase`, сессии — их статус и уникальные ограничения, стрик — `UserDay.streakAppliedAt`, cron-напоминания — отдельная `ReminderDelivery`.
- События не ставятся в очередь и не сохраняются временно для последующей догрузки. После включения event log событийная история начнётся с момента включения; агрегаты за более ранний период разрешено строить из `Session`, `SessionCard`, `UserWord` и `UserDay`.

**Типы событий:**
`CARD_KNOWN` · `CARD_UNKNOWN` · `TEST_CORRECT` · `TEST_WRONG` · `SESSION_FINISHED` · `SESSION_ABANDONED` · `SHIELD_USED`

События админских действий, экономики, покупок, напоминаний, редактирования контента, milestone-сообщений и технических операций не определяются и не передаются в `EventSink`. Их актуальное состояние и идемпотентность обеспечивают профильные таблицы (`CurrencyTransaction`, `Purchase`, `ReminderDelivery`, `UserDay` и другие), а техническая диагностика выполняется через pino.

**Поля события при будущем включении хранения:**
`id · idempotencyKey · userId · timestamp · eventType · sessionId · cardId · answer · responseTimeMs`

### 5.1. Идемпотентность и повторная доставка

Любая операция, которая меняет прогресс, баланс или стрик, выполняется в транзакции и имеет уникальный ключ идемпотентности. Повторная операция возвращает уже сохранённый результат и ничего не начисляет повторно.

- **Повторная доставка Telegram update:** `update_id` резервируется в `ProcessedTelegramUpdate` в той же транзакции, что и изменение состояния; уже обработанный update не выполняется повторно.
- **Двойное нажатие `Знаю`/`Не знаю`:** действие идентифицируется по уникальному `callback_query.id`, сохраняемому как `SessionCard.answerActionId`. Атомарный `UPDATE ... WHERE answeredAt IS NULL` допускает только первый ответ; повторный callback безопасно игнорируется.
- **Повторная награда за сессию:** награда имеет ключ `SESSION_REWARD:{sessionId}` и создаётся только один раз.
- **Одновременная покупка:** покупка имеет ключ `PURCHASE:{userId}:{requestId}`, где `requestId` — это `callback_query.id` из Telegram (гарантированно уникален для конкретного нажатия кнопки, не генерируется вручную клиентом). Атомарный условный `UPDATE` баланса и создание `Purchase`/`CurrencyTransaction` выполняются в одной короткой транзакции; если баланс недостаточен, `UPDATE` не затрагивает строку.
- Идемпотентность распространяется также на начисление стрика, сюрпризы и ручные админские начисления. Любое изменение баланса создаёт `CurrencyTransaction`; ключ операции уникален, а сохранённый `balanceAfter` позволяет вернуть результат повтора.
- **Никаких вызовов Telegram внутри транзакции БД.** Транзакция только меняет состояние и возвращает описание того, что нужно отправить; фактическая отправка/редактирование сообщений выполняется после успешного коммита. Сбой отправки не откатывает уже зафиксированный прогресс и логируется.

**Формат ключа события.** Сформированное событие всегда получает `idempotencyKey` по правилу `{EVENT_TYPE}:{scope}`, даже когда `NoopEventSink` его отбрасывает. При будущем включении `Event.idempotencyKey` обязателен и уникален:

| Событие | `scope` |
| --- | --- |
| `SESSION_FINISHED`, `SESSION_ABANDONED` | `{sessionId}` |
| `CARD_KNOWN`, `CARD_UNKNOWN`, `TEST_CORRECT`, `TEST_WRONG` | `{cardId}` |
| `SHIELD_USED` | `{userId}:{localDate}` |

Префикс типа события гарантирует отсутствие конфликтов между разными статистическими фактами. `CARD_KNOWN`/`CARD_UNKNOWN`, `TEST_CORRECT`/`TEST_WRONG` и `SESSION_FINISHED`/`SESSION_ABANDONED` попарно взаимоисключающие для одного `scope`.

В БД `Event.idempotencyKey` и `Purchase.idempotencyKey` имеют уникальный индекс. Уникальность `Event` является дополнительной защитой только после включения event log; результат бизнес-операции никогда не определяется наличием строки `Event`.

## 6. Напоминания и сообщения (рабочие тексты в БД, seed/fallback в `src/content/`)

Runtime-тексты используют именованные placeholders вида `{streak}` и `{currency}`. Для каждого стабильного ключа разрешённый набор placeholders описан в типизированном реестре в коде; неизвестный или пропущенный placeholder запрещает сохранение через админку. Динамические значения экранируются перед отправкой в Telegram HTML, сами тексты валидируются пробным рендером. При ошибке записи из БД сервис логирует ключ без содержимого сообщения и использует seed/fallback.

### 6.1. Утреннее напоминание (час настраивается пользователем)

Отправляется **каждое утро** в `User.reminderHour:00` по локальному времени пользователя (`User.timezone`), безусловно — статус сегодняшнего `UserDay` не подавляет его. Повторная отправка в ту же локальную дату запрещена записью `ReminderDelivery` с ключом `MORNING:{userId}:{localDate}` (§5.1). Событие для напоминания не формируется. Если пользователь выбрал более ранний час в тот же день после отправки, повторное сообщение не приходит; новый час начинает действовать со следующей локальной даты.

Содержание: приятность + саммари (стрик, цели дня) + блок «Слово дня», если оно задано на эту дату (§6.5). Кнопка `▶️ Начать обучение`.

### 6.2. Вечернее в 21:00, если стрик не обновлён

Тёплое: «стрик прервётся, пройди урок». Кнопка `▶️ Начать`. **Без давления.**

### 6.3. Похвалы за события

За стрик-вехи, новый личный рекорд, сохранение стрика щитом, досрочное закрытие дня, X пройденных уроков сегодня, за сессию без ошибок и т.д. Для каждого события хранятся несколько случайных вариантов в runtime-контенте.

### 6.4. Milestone-сообщения «от меня» (сюрпризы)

Легко добавлять новые и менять текста. Примеры:

- 7 дней: «7 дней польского. Кажется, кто-то становится полькой 😌»
- сложная сессия: «Сегодня было тяжеловато, но ты всё равно дошла до конца. Вот тебе солнышко ☀️»
- рандом без причины: «Я просто решил тебя сегодня немного порадовать ☀️»
- вне учёбы: «Кстати, я тебя люблю. Всё, можешь продолжать учить польский ❤️»

> **Правило:** награда/сообщение **не должны быть предсказуемыми** — иногда это сюрприз.

После первой полностью завершённой сессии календарного дня бот один раз генерирует число криптографически стойким генератором. С вероятностью `10%` начисляется равновероятно `1`, `2` или `3` единицы валюты. Ключ `SURPRISE:{userId}:{localDate}` в `CurrencyTransaction` гарантирует не более одного сюрприза в сутки; отдельное событие не формируется, сюрприз не входит в учебный дневной лимит. В тестах генератор случайности подменяется детерминированным.

> Тексты выше — примеры seed-контента с названием валюты по умолчанию. При переименовании валюты через экран `Валюта` старые тексты не переписываются автоматически; новые тексты рекомендуется добавлять с учётом актуального названия.

### 6.4.1. Досрочный стрик (после 3 полных сессий)

```
🌙 Ты сегодня уже достаточно постаралась.
Хочешь закрыть завтрашний день заранее?
[Активировать] [Не сейчас]
```

### 6.5. ❤️ Слово дня (отдельная механика)

Автор заранее задаёт слово дня на конкретную дату, напр. `kocham — любить`. `WordOfDay` хранит `polish`/`russian` самостоятельно, отдельно от пользовательского словаря (`Word`) — слово дня не обязано существовать в словаре и не создаёт там запись.

- В админке есть экран назначения, замены и удаления `WordOfDay` на выбранную локальную дату; на одну дату допускается одна запись. Ввод разбит на два шага: сначала дата и польское слово, затем отдельным сообщением — русский перевод; запись сохраняется только после обоих шагов.
- **Место показа** — утреннее напоминание (§6.1) и главное меню (§4.1). Если запись на текущую локальную дату есть, добавляется блок вида: `❤️ Слово дня: kocham — любить`; в напоминании также идёт короткая тёплая фраза из runtime-контента, например «Сегодня я хочу, чтобы ты запомнила именно это слово ❤️».
- Если запись `WordOfDay` на текущую дату отсутствует, блок просто не показывается (тихий пропуск, без ошибки) ни в напоминании, ни в главном меню. Слово дня не влияет на подбор карточек, награды и стрик; отдельного сообщения «после изучения» нет.

## 8. Экономика (простая и интересная)

> Суммы ниже выражены в единицах валюты; название и иконка для отображения берутся из `CurrencyConfig` (по умолчанию ☀️ «солнышко», см. §3.1).

- **Обычная сессия:** `+5` солнышек только за полностью пройденный зафиксированный план из `1–10` карточек; ответ `Знаю` и `Не знаю` имеют одинаковый вес. Досрочно завершённая сессия награды не даёт.
- **Тест:** `+10` солнышек только за полностью пройденные `10` вопросов.
- **Дневной лимит:** максимум `20` солнышек за обучение. Награда не делится на части: если полная награда не помещается в лимит, она не начисляется.
- При достижении лимита бот не ругает пользователя и не блокирует обучение: он засчитывает полностью пройденную сессию и показывает милое сообщение с предложением отдохнуть.
- **Сюрприз:** `+1–3`, максимум один раз в сутки, сверх дневного лимита обучения.
- **Маленький подарок:** `120` солнышек, примерно одна недельная цель при обычном ритме обучения.
- **Особый подарок:** `350` солнышек, долгосрочная цель на несколько недель (самый дорогой в магазине).
- **Щит на стрик:** `25` солнышек, покупается многократно, суммируется и применяется автоматически при пропуске дня.
- Подарки не дают валюту обратно; админское начисление не считается обучением и не влияет на дневные лимиты.
- При дневном лимите обучения `20` пользователь может накопить максимум `140` солнышек за неделю без учёта сюрпризов, поэтому маленький подарок не покупается чаще примерно одного раза в неделю.
- Значения цен, наград и лимитов вынесены в `economy config`, но изменение конфигурации не переписывает историю уже совершённых операций.
- Каждый товар имеет стабильный код в `economy config`: `GIFT_SMALL`, `GIFT_SPECIAL`, `SHIELD`. Именно этот код (а не отображаемое название) сохраняется в `Purchase.item` и логах, чтобы переименование товара не ломало историю покупок.

## 9. Нормативная логическая модель данных

Ниже зафиксированы обязательные таблицы, поля и индексы. В Фазе 0 агент преобразует эту логическую модель в валидный для выбранной зафиксированной версии Prisma полный `schema.prisma`: добавляет relation-поля, внешние ключи и обратные связи, не меняя описанную семантику. Ручные возможности SQLite, которых нет в Prisma DSL, оформляются SQL в migration и покрываются интеграционными тестами.

**Ограничения провайдера (проверено на Prisma 7 + SQLite).** Prisma не поддерживает для SQLite ни `enum`, ни скалярный тип `Json`, поэтому статусы и типы хранятся как `String`, а `SessionCard.options` — как JSON-строка. Допустимые значения задаются типами TypeScript и проверяются Zod при записи и чтении. Начиная с Prisma 7 URL подключения задаётся в `prisma.config.ts`, а не в `schema.prisma`; `PrismaClient` создаётся с driver adapter.

```prisma
datasource db {
  provider = "sqlite"
}

model User {
  id             Int      @id @default(autoincrement())
  telegramId     BigInt   @unique
  firstName      String? // из Telegram, для отображения в админке; обновляется при каждом обращении
  username       String? // из Telegram, без @, может отсутствовать; обновляется при каждом обращении
  currencyBalance Int     @default(0) // баланс валюты; название/иконка настраиваются отдельно в CurrencyConfig
  currentStreak  Int      @default(0)
  maxStreak      Int      @default(0)
  shields        Int      @default(0) // щиты, применяются автоматически при пропуске дня
  reminderHour   Int      @default(10) // час утреннего напоминания 0..23, минуты всегда :00; валидируется Zod
  timezone       String   @default("Europe/Minsk") // IANA timezone пользователя; выбор в UI — расширение будущей версии (см. §4.7)
  createdAt      DateTime @default(now())
  // ...
}

model Category {
  id        Int      @id @default(autoincrement())
  name      String
  ownerId   Int?     // null = системная
  isActive  Boolean  @default(true)
  words     Word[]
  @@unique([name, ownerId])
}

model Word {
  id            Int      @id @default(autoincrement())
  categoryId    Int
  polish        String
  russian       String
  transcription String?  // на будущее
  example       String?  // пример предложения, на будущее
  ownerId       Int?
  isActive      Boolean  @default(true)
  @@unique([categoryId, polish, ownerId])
}

model UserWord {              // прогресс: user + word
  userId            Int
  wordId            Int
  firstSeenAt       DateTime?
  lastSeenAt        DateTime?
  timesSeen         Int      @default(0)
  timesKnown        Int      @default(0)
  timesUnknown      Int      @default(0)
  currentScore      Float    @default(0) // непрерывная «уверенность» (растёт на Знаю, падает на Не знаю); используется в статистике "самое лёгкое/сложное слово"
  currentLevel      Int      @default(0) // 0=новое, 1=незнакомое, 2=знакомое — приоритет показа карточек, см. §4.2
  lastAnswer        String?
  lastAnswerAt      DateTime?
  consecutiveKnown  Int      @default(0)
  consecutiveUnknown Int     @default(0)
  testSeenCount    Int      @default(0) // сколько раз слово было целью вопроса теста (инкремент при показе вопроса)
  testCorrectCount Int      @default(0)
  testWrongCount   Int      @default(0)
  firstLearnedAt   DateTime?
  timesSeenToLearn Int?
  nextReviewAt      DateTime? // если в будущем — слово временно исключено из подбора карточек (см. §4.2, повторный «Знаю» после «Не знаю»)
  @@id([userId, wordId])
  @@index([userId, currentLevel])
  @@index([userId, nextReviewAt])
}

model Session {
  id            Int      @id @default(autoincrement())
  userId        Int
  mode          String   // FLASHCARDS | TEST
  categoryId    Int?     // категория для FLASHCARDS; null для TEST (вопросы из разных категорий)
  direction     String?  // PL_RU | RU_PL — режим карточки; у TEST всегда PL_RU
  status        String   @default("ACTIVE") // ACTIVE | COMPLETED | ABANDONED
  plannedCount  Int      // 1..10 для FLASHCARDS, ровно 10 для TEST
  answeredCount Int      @default(0)
  isFull        Boolean  @default(false) // true, если отвечены все plannedCount карточек
  rewardedAt    DateTime?
  startedAt     DateTime @default(now())
  finishedAt    DateTime?

  @@index([userId, status])
  @@index([userId, startedAt])
}

model SessionCard {
  id             Int      @id @default(autoincrement())
  sessionId      Int
  wordId         Int
  categoryId     Int
  position       Int
  promptText     String // снимок показываемого слова; план не зависит от последующего изменения Word
  translationText String? // снимок перевода для FLASHCARDS; показывается после «Не знаю» (§4.2)
  options        String?  // JSON-строка: [{ wordId, label }] длиной 4; порядок совпадает с кнопками
  correctOption  Int?     // позиция правильного ответа: 0..3
  selectedOption Int?     // выбранная пользователем позиция: 0..3
  answerActionId String?   @unique // callback_query.id первого принятого ответа
  answer         String?  // KNOW, UNKNOWN или TEST_OPTION
  isCorrect      Boolean?
  shownAt        DateTime? // заполняется в момент фактического показа, а не при создании плана
  answeredAt     DateTime?

  @@unique([sessionId, position])
  @@index([sessionId, wordId])
}

model UserDay {
```

> Составные уникальные индексы `[name, ownerId]` и `[categoryId, polish, ownerId]` защищают от дублей категорий/слов у одного владельца. В SQLite `NULL` в уникальном индексе считается отличным от другого `NULL`, поэтому для системных записей (`ownerId = null`) этот индекс не запрещает дубликаты на уровне БД — для seed-данных уникальность нужно контролировать на уровне сервиса.

> Отдельный `UserWord` со всеми счётчиками и `nextReviewAt` позволяет позже добавить spaced repetition **без переписывания системы**.

> `ReminderDelivery` создаётся до вызова Telegram и запрещает вторую попытку для того же типа и локальной даты. После успешной отправки заполняется `sentAt`; при неопределённом сетевом результате повтор не выполняется, то есть для напоминаний выбирается семантика at-most-once вместо риска прислать два одинаковых сообщения.

> В итоговой Prisma-схеме добавляются relation-поля и внешние ключи. Статусы и типы остаются `String`, потому что Prisma не поддерживает `enum` для SQLite; допустимые значения задаются типами TypeScript и валидируются Zod на границах. Для единственной активной сессии migration содержит ручной частичный уникальный индекс: `CREATE UNIQUE INDEX "Session_userId_active_key" ON "Session"("userId") WHERE "status" = 'ACTIVE'`.

> **Правила удаления.** Прикладной код не выполняет физическое удаление `Category`, `Word`, `SessionCard` и связанных доменных записей. Внешние ключи контента используют `onDelete: Restrict`, чтобы случайный прямой `DELETE` не уничтожил историю. Пользовательские и админские операции меняют только `isActive` по правилам §3.4.

> `AdminAdjustment` — операционный журнал только для ручных начислений и восстановления стрика; он не является пользовательским `Event` и не подключается к `EventSink`. Повтор операции возвращает результат по `idempotencyKey` и не применяет изменение второй раз.

## 11. Нефункциональные требования

- **Локализация текстов:** весь UI и сообщения — на русском.
- **Runtime-тексты:** изменения текста применяются без rebuild и перезапуска; задержка при прямом изменении БД не более TTL (30 секунд).
- **Расширяемость текстов:** новый вариант добавляется через админку или seed без изменения бизнес-логики.
- **Надёжность текстов:** если запись отсутствует или временно недоступна, используется seed/fallback; пустой активный текст запрещён валидацией.
- **Надёжность стрика:** переход дня считается строго по таймзоне пользователя (`User.timezone`, по умолчанию `Europe/Minsk`).
- **Идемпотентность наград:** одна сессия начисляет валюту один раз.
- **Runtime-конфигурация валюты:** название и иконка валюты редактируются админом и применяются без rebuild и перезапуска (см. `CurrencyConfig`, §9); по умолчанию используется ☀️ «солнышко». Поля `icon`/`nameOne`/`nameFew`/`nameMany` не могут быть пустыми — валидация при сохранении через экран `Валюта` (аналогично запрету пустого активного текста выше).
- **Идемпотентность операций:** повторный Telegram update, callback, ответ, покупка или отправка напоминания не должны повторно менять состояние или отправлять награду.
- **Атомарность экономики:** баланс никогда не уходит в минус; параллельные покупки используют условный `UPDATE ... WHERE currencyBalance >= cost` внутри короткой SQLite-транзакции.
- **Время и тестируемость:** для явного преобразования времени используется Luxon; бизнес-сервисы получают `Clock` и генератор случайных чисел как зависимости.
- **Логи:** pino пишет структурированные события с `eventType`, `userId`, `sessionId` и ошибкой; токены, `.env`, тексты личных сообщений и callback payload целиком не логируются.
- **Event log:** при `EVENT_LOG_ENABLED=false` операции из §5 формируют те же статистические события, но `NoopEventSink` выполняет `0` SQL-запросов; остальные операции событий не формируют, pino не используется как скрытая замена истории.
- **Завершение процесса:** при `SIGTERM/SIGINT` бот прекращает принимать новые update, дожидается текущих транзакций и закрывает Prisma; незавершённая транзакция откатывается, активная сессия восстанавливается при следующем запуске.
- **База данных:** SQLite-файл хранится только в Railway volume `/data`; `prisma migrate deploy` выполняется в startup-команде до запуска long polling, поскольку volume недоступен в pre-deploy container. Резервное копирование не выполняется, потеря данных считается допустимым риском.
- **Приватность:** доступ по белому списку; данные только для админа.
- **Тон бота:** поддержка без давления (эмоциональное давление = 0).

### 11.1. Определения статистики

- Основной источник агрегатов за весь период — доменные таблицы `Session`, `SessionCard`, `UserWord` и `UserDay`, поэтому период работы с `NoopEventSink` не теряется. После включения event log события из §5 используются для детальной временной линии и сверки, но не заменяют доменные таблицы как source of truth. Экран §4.6 не читает `Event`.
- `выучено слов` — число активных слов с `UserWord.currentLevel = 2`; `изучено карточек` — число принятых ответов `KNOW/UNKNOWN`; `тестов` — число завершённых тестов.
- `% правильных` — число `SessionCard.isCorrect = true`, делённое на число тестовых карточек с заполненным `isCorrect`, умноженное на `100`; при отсутствии ответов показывается `—`, а не `0%`. После включения event log эквивалентная проверочная формула — `TEST_CORRECT / (TEST_CORRECT + TEST_WRONG) × 100`.
- `дней обучения` — число уникальных `UserDay` со статусом `COMPLETED`; `пропущено дней` — число `MISSED`, созданных после первого дня обучения; `использовано щитов` — число `SHIELDED`.
- Время сессии — от `startedAt` до `finishedAt`; активные сессии не входят в агрегаты. Средняя и максимальная длительность считаются по `COMPLETED` и `ABANDONED`, имеющим `finishedAt`.
- Любимое время и день недели определяются по `startedAt` завершённых и досрочно законченных сессий в таймзоне пользователя (`User.timezone`); при равенстве выбирается более ранний бакет или день. Среднее число сессий в день — число таких сессий, делённое на число календарных дней от первой сессии до сегодня включительно.
- Самое лёгкое и сложное слово определяется по `currentScore` среди слов с `timesSeen > 0`; чаще всего забываемое — максимум `timesUnknown`. Быстрее всего выученное — минимальный `timesSeenToLearn`, больше всего повторений — максимальный `timesSeenToLearn`; поля фиксируются один раз при первом достижении уровня `2` и не очищаются при последующем снижении уровня. При равенстве показывается слово, достигшее результата раньше.

### 11.2. Проверяемые критерии приёмки

- Два параллельных запроса запуска создают ровно одну `ACTIVE`-сессию; повторный Telegram update и двойной callback изменяют прогресс один раз.
- Категория с `1–9` активными словами создаёт план соответствующего размера без повторов; ответ на последнюю карточку даёт обычные награду и стрик. Категория без слов не создаёт сессию.
- Завершение около полуночи относится к локальной дате фактического `finishedAt` в таймзоне пользователя (`User.timezone`); тесты перехода дня используют внедряемый `Clock`.
- Несколько пропущенных дней последовательно расходуют по одному щиту; `EARLY` применяется раньше щита; при нехватке щитов серия обрывается один раз и текущая полная сессия начинает её с `1`.
- Перезапуск во время карточек или теста восстанавливает тот же вопрос и сохранённые варианты; изменение или деактивация исходного слова не меняет активную сессию.
- Две параллельные покупки при недостаточном общем балансе допускают только одну успешную транзакцию, и баланс никогда не становится отрицательным.
- Все четыре варианта теста принадлежат одной категории и имеют различные нормализованные русские подписи; категория с меньшим числом подходящих вариантов исключается.
- При достаточном пуле цель не повторяется семь следующих вопросов и не появляется более двух раз в тесте; при малом пуле применяется описанный fallback без зависания генератора.
- Вечернее напоминание отправляется ровно в `21:00` по локальному времени пользователя и не отправляется повторно для того же пользователя и локальной даты.
- Изменение валюты и runtime-текста применяется к новым сообщениям сразу после изменения через админку и не позднее 30 секунд после прямого изменения БД.
- Саммари категории (§4.2.1) верно считает «Всего/Выучено/Осталось/Нужно повторить» сразу после ответа на карточку в этой же категории.
- Слово, отвеченное «Знаю» сразу после «Не знаю», получает `nextReviewAt` в будущем и не попадает в план, пока в категории есть достаточно слов без активного кулдауна.
- Если все активные слова категории на кулдауне, сессия всё равно создаётся и добирает слова в порядке возрастания `nextReviewAt`, без повторов внутри плана (§4.2).
- Повторный запуск seed на непустой БД не создаёт дублей и не перезаписывает отредактированные админом `CurrencyConfig`, `EconomyConfig` и `ContentText` (§2.1).
- Утреннее напоминание приходит каждый день в `User.reminderHour:00` и ровно один раз на локальную дату; изменение часа после отправки не вызывает повтора в тот же день.
- Холостой минутный cron-тик выполняет `0` SQL-запросов и `0` вызовов Telegram API; после изменения `reminderHour` реестр планировщика обновляется без перезапуска и новое значение применяется со следующего тика.
- При `EVENT_LOG_ENABLED=false` полный сценарий не создаёт ни одной строки `Event`; тестовый `EventSink` получает только `CARD_KNOWN`, `CARD_UNKNOWN`, `TEST_CORRECT`, `TEST_WRONG`, `SESSION_FINISHED`, `SESSION_ABANDONED`, `SHIELD_USED`, а покупки, начисления, напоминания и админские операции не передают события.
- Два параллельных списания в SQLite при балансе только на одну покупку дают ровно один успешный условный `UPDATE`; временный `SQLITE_BUSY` обрабатывается ограниченным retry и не приводит к двойной операции.
- После redeploy данные SQLite сохраняются в `/data/kartochki.db`; при недоступном volume или ошибке `prisma migrate deploy` бот не запускает long polling. Startup-проверка подтверждает `journal_mode=WAL` и `foreign_keys=ON`.
- Создание плана обычной сессии или теста не выполняет N+1-запросов: число SQL-запросов ограничено константой и не растёт вместе с числом создаваемых `SessionCard`.
- Админская деактивация категории выставляет `isActive = false` ей и всем её словам в одной транзакции, не удаляет `UserWord`, `SessionCard`, `WordOfDay` и события, не меняет баланс и не прерывает активную сессию; новые планы этот контент не используют.
- Пользовательская деактивация категории выставляет `isActive = false` ей и всем её словам в одной транзакции; строки и история сохраняются.
- При двух пользователях каждый видит системный и собственный активный контент, но не видит и не может изменить контент другого пользователя; планы, тесты и саммари соблюдают тот же фильтр.
- Повтор ручного начисления или восстановления стрика с тем же `requestId` не меняет состояние второй раз и создаёт ровно одну `AdminAdjustment` с исходной причиной.
- Повторное подтверждение разового сообщения с тем же `requestId` не отправляет его второй раз; создаётся ровно одна запись `AdminMessage`.
